# Nimbus Dashboard — Feature PRD

**Status: draft, awaiting confirmation. Nothing in this document is
approved for implementation.** This is a catalog to choose from, not a
build plan — no feature here should be started until it's explicitly
picked.

## 1. Purpose & scope

This document catalogs candidate dashboard improvements for Nimbus,
researched against Google Drive, Google Photos, and Box's current
(2025-2026) feature sets, and organized small → big within categories.
Its job is to give the product owner (Ankush) a complete menu to choose
from — which items to build, in what order — rather than to prescribe
one. Every entry is scored for effort and checked against Nimbus's actual
architecture and budget, so "inspired by Drive" doesn't quietly become
"assumes an enterprise backend team." Items that don't fit the
architecture without a real cost or complexity jump are labeled as such,
not smoothed over.

## 2. Current state snapshot (what's already shipped)

So this reads as additive, not duplicative:

- **Auth**: email/password + Google/GitHub OAuth, link-by-email, JWT
  access tokens (24h, memory-only) + httpOnly refresh cookie, bcrypt.
- **Files**: folder tree with move/rename, trash → restore → permanent
  delete (30-day retention job), filename-substring search, infinite
  scroll, multi-select with an always-visible select-all bar, drag-and-
  drop upload with per-file progress, direct-to-S3 presigned uploads.
- **Views**: "My Cloud" (tree), Photos (cross-folder, image-only,
  newest-first), Videos (same pattern, video-only), Recent, Trash.
- **Preview**: a Lightbox that plays images, PDFs, video, and audio
  inline; anything else falls back to download.
- **Settings page**: Profile (name, connected sign-in methods), Storage
  (editable *display* quota — cosmetic, not enforced), Security
  (change/set password), About.
- **Thumbnails**: automatic for images only, generated by a separate
  Lambda on S3 upload. No video thumbnail generation.
- **Mobile**: responsive layout, drawer sidebar, touch targets, icon-only
  toolbar under 620px, OverflowMenu pattern instead of per-row icon
  clutter.
- **23 file endpoints, 10 auth endpoints**, ~171 backend tests, tsc/
  eslint/build enforced in CI.

**Not built**: any form of sharing or collaboration, file versioning,
content search (search is filename-only), a native mobile app,
real-time co-editing (there's no document format or editor — Nimbus
stores files, it doesn't edit them).

## 3. Architectural constraints that shape feasibility

These aren't preferences — they're why several Drive/Box features below
are marked infeasible-as-is rather than merely "large":

- **No EC2, no always-on compute, no Kubernetes.** Everything runs on
  Lambda (request-billed) or doesn't run at all. Anything needing a
  long-lived process (a job queue worker, a search-indexing daemon, a
  virus-scan service polling a queue) needs a serverless-native
  redesign, not a lift-and-shift of how Drive/Box would build it.
- **Budget ceiling ~₹200/month, forever**, and that's *already* fully
  spent on S3 storage. Any new AWS service must fit inside its own free
  tier at personal scale — it cannot add to the recurring bill.
- **No Route 53, no Secrets Manager.** Rules out anything assuming a
  custom domain with managed DNS, or a secrets vault beyond Lambda env
  vars.
- **MongoDB Atlas M0 is 512MB, shared-tier.** Fine for metadata; wrong
  place for anything at real volume (activity logs, full-text indexes
  over file contents, embeddings).
- **Solo maintainer.** No admin console, no enterprise compliance
  tooling (retention holds, DLP, watermark policies) makes sense for an
  audience of one to a handful of people. Box's entire governance
  surface is aimed at a persona this project doesn't have.
- **No ML/vision pipeline today.** Thumbnailing is deterministic
  (Pillow resize). Anything claiming "smart" (face grouping, semantic
  search, auto-tagging) needs either a paid inference API (real,
  ongoing cost per call) or a model running somewhere (compute cost) —
  neither is free at any real usage volume. These are flagged per-item
  below rather than assumed impossible, since usage here is small
  enough that per-call inference pricing might still be negligible —
  but it is a cost that doesn't exist today and would need a explicit
  yes.

## 4. Feature catalog

Complexity: **S** (hours), **M** (a few days), **L** (a week+),
**XL** (needs its own design pass before estimating).
Infra: **FE** (frontend-only), **BE** (new/changed backend, same
services), **NEW-INFRA** (needs a new AWS resource or architecture
decision).

### 4.1 Organization & Navigation

| Feature | Inspiration | Complexity | Infra | Feasibility |
|---|---|---|---|---|
| Keyboard shortcuts reference/cheat-sheet (`?` opens a panel) | Drive | S | FE | Trivial — some shortcuts already exist (`/` search, Cmd+A, Delete), just undocumented. |
| Sort persistence per-folder (remember last sort choice) | Drive | S | FE (localStorage) | No backend change needed. |
| Breadcrumb dropdown (jump to any ancestor, not just click-back) | Drive, Box | S | FE | Breadcrumbs already exist; this is a UI enhancement on top. |
| Grid view / list view toggle for "My Cloud" (not just Photos) | Drive | M | FE | Needs a second FileRow layout; state is trivial. |
| Starred / pinned items | Drive | M | BE + FE | New boolean field on `Item`, a new filtered view, a toggle in OverflowMenu. Small, real backend change. |
| Color-coded / custom folder icons | Drive | M | BE + FE | New field on folders, a color picker UI. Cosmetic only. |
| Nested "Shared with me" / cross-account visibility | Drive | XL | NEW-INFRA | Meaningless until sharing (4.4) exists — sequencing dependency, not a standalone feature. |
| "Organize my folder" AI suggestions | Drive (2026) | XL | NEW-INFRA | Needs an LLM call per suggestion — real per-request cost, and meaningfully hard to get right. Not worth it at this scale; flagged as inspiration only. |

### 4.2 Search & Discovery

| Feature | Inspiration | Complexity | Infra | Feasibility |
|---|---|---|---|---|
| Search filters (type, date range, size) as UI on top of existing search | Drive's search operators | S–M | FE + BE | Backend `search()` already takes a term; adding structured filters is a query-shape change, not new infra. |
| Search-as-you-type result preview dropdown | Drive | M | FE | Reuses existing `/files/search`. |
| Full-text search *inside* documents (PDF/text content) | Drive | XL | NEW-INFRA | Needs a text-extraction step at upload time and a real search index (Mongo Atlas M0 has no full-text search at usable scale). Realistic path: extract text into a Mongo field and use a regex/`$text` index — doable within free tier for personal-scale document counts, but is a genuine multi-day feature, not a search filter. |
| Semantic/natural-language search ("photos from my Goa trip") | Google Photos | XL | NEW-INFRA | Needs embeddings + a vector index or an LLM call per search. Real recurring cost per query. Explicitly cut in `requirements.md` §6 already — restating here as still out of scope. |
| Saved searches | Box | S | FE (localStorage) or BE (M) | Cosmetic if client-only; a "shared saved search" would need backend storage. |

### 4.3 Media & Photos

| Feature | Inspiration | Complexity | Infra | Feasibility |
|---|---|---|---|---|
| Favorites / hearted photos | Google Photos | M | BE + FE | Same shape as "starred" above — could be the same underlying field. |
| Map view (photos plotted by GPS EXIF) | Google Photos | L | FE + BE | EXIF GPS is likely already extracted for `taken_at`; check what's captured today and extend to lat/long. Rendering needs a map tile provider — OpenStreetMap tiles are free, Google Maps embeds are not at volume. |
| Duplicate detection | Google Photos | M–L | BE (opportunistic) | Perceptual hashing (pHash) computed in the *existing* thumbnailer Lambda when it already touches the image — no new service. Flagging duplicates for the user to review, not auto-deleting. |
| "On this day" / memories resurfacing | Google Photos | M | FE + BE | Pure query against existing `taken_at` field, no new infra — an underrated quick win. |
| Photo Stacks (auto-group visually similar/burst shots) | Google Photos | L | BE (opportunistic) | Reuses the pHash work from duplicate detection — group near-identical hashes taken close in time instead of just flagging them. |
| Basic in-browser edit (crop, rotate, brightness) | Google Photos | M | FE | Canvas API, client-side only, writes a new version on save. Depends on 4.6 (versioning) existing, or overwrites the original — a real product decision either way. |
| Auto face-grouping | Google Photos | XL | NEW-INFRA, real cost | Needs an ML model (on-device inference or a paid vision API per photo). Meaningfully out of scope without a specific budget decision — flagged as inspiration only, not a near-term candidate. |
| Slideshow / cast to TV | Google Photos | M | FE | Slideshow is pure frontend. Casting needs Chromecast/AirPlay APIs — doable but niche for this audience. |
| Video thumbnails (currently missing) | (Nimbus gap, not from research) | M | NEW-INFRA (small) | The thumbnailer Lambda only runs Pillow (images). Video frame extraction needs ffmpeg, which isn't in the Lambda runtime and would need a Lambda layer (~tens of MB, still fits in the free tier, but is new packaging work and a real "does this still fit in a serverless function's time/memory limit" question for large videos). |

### 4.4 Sharing & Access

| Feature | Inspiration | Complexity | Infra | Feasibility |
|---|---|---|---|---|
| Public read-only link for a single file | Drive | M | BE + FE | Needs a new "share token" concept issuing a scoped, revocable link — separate from the presigned S3 URLs used internally (those expire in minutes by design, wrong tool for a shareable link). This is the load-bearing feature everything else in this section depends on. |
| Link expiry | Drive, Box | S (once above exists) | BE | Just a TTL field on the share-token record. |
| Folder sharing (shares everything inside) | Drive | M (once single-file sharing exists) | BE | Same token concept, scoped to a subtree. |
| Named-recipient sharing (not just "anyone with the link") | Drive, Box | L | BE + auth | Needs the recipient to either have a Nimbus account or a lightweight guest-auth flow. Real scope increase — this is where "sharing" stops being small. |
| Multi-user collaboration on the same file | Drive, Box | XL | Out of scope | No document format or editor exists in Nimbus at all — this isn't a missing feature, it's a missing product category. Would require building or embedding an editor, which is a different project. |
| Watermarking / DLP / retention holds | Box | XL | Out of scope | Enterprise-compliance tooling for an audience Nimbus doesn't have (solo/small group, not a regulated org). Explicitly not recommended regardless of effort. |

| Feature | Inspiration | Complexity | Infra | Feasibility |
|---|---|---|---|---|
| Folder upload (drag a whole folder, preserve structure) | Drive | M | FE | Browser File System APIs support this; backend already accepts arbitrary `parent_id` per file. |
| Paste-to-upload (Ctrl+V an image from clipboard) | Drive, Photos | S | FE | Clipboard API + existing upload path. |
| Resumable/chunked upload for large files | Drive | L | BE + FE | Presigned single-PUT uploads (current approach) have a practical per-file ceiling; true resumability needs S3 multipart upload, which is a real backend change (multiple presigned URLs per file, a completion step per part). |---|---|---|---|---|
| Bulk rename (pattern-based, e.g. add a prefix to N selected files) | (common power-user ask, not Drive-native) | M | FE + BE | Backend rename endpoint already exists per-item; this is a client-side loop with a preview step. |

## 5. Explicit non-goals

Stated plainly, matching this codebase's existing honesty style:

- **Real-time collaborative document editing.** Nimbus has no document
  format or editor. This isn't a gap in the file manager — it's a
  different product.
- **Enterprise governance tooling** (retention holds, legal holds, DLP,
  watermark policies, admin console). Box's entire compliance surface
  targets regulated organizations; Nimbus's audience is a person or a
  handful of people.
- **A desktop sync client / background folder watcher.** Different
  distribution model, different codebase, out of scope for "the
  dashboard."
- **Semantic/AI-powered search and auto face-grouping**, at least
  without an explicit decision to take on real per-call inference cost.
  Already cut once in `requirements.md` §6 — restated here so it doesn't
  quietly resurface as "just add AI search."
- **A native mobile app.** The PWA path (4.12) gets most of the benefit
  (installable, works offline-ish) without the app-store distribution
  and separate-codebase cost.
- **Anything requiring EC2, Kubernetes, Route 53, or Secrets Manager**,
  per the hard constraints in `CLAUDE.md` — restated here because a few
  items above (full-text search infra, an activity-log pipeline) could
  tempt a "just spin up a small always-on service" shortcut that this
  project has already ruled out for durable reasons.

## 6. Suggested phasing (options, not a plan)

Grouped by rough effort, **not** in build order — sequencing is Ankush's
call, not this document's.

**Quick wins** (S, frontend-only or trivial backend, days not weeks):
keyboard shortcuts panel, sort persistence, breadcrumb dropdown,
zoom/pan on preview, print from preview, paste-to-upload, upload-complete
notification, default view preference, sign-out-everywhere button,
reduced-motion setting, PWA manifest, storage-by-type chart, "On this
day" resurfacing.

**Medium efforts** (a few days each, real but contained backend change):
starred/favorites, grid/list toggle, search filters, duplicate detection
(opportunistic in the thumbnailer), map view, bulk rename, drag-to-move,
right-click menu, undo toast, storage-almost-full banner, session
management UI, login activity log, locked folder, video thumbnails
(needs an ffmpeg Lambda layer decision).

**Large efforts needing their own design discussion first** (each of
these deserves a scoped conversation before estimating further, not a
line-item estimate here): public share links (the load-bearing piece
sharing depends on), file versioning (S3 storage-cost implication),
resumable/chunked large-file upload, full-text document search,
two-factor authentication, an activity-log pipeline, client-side/E2E
encryption.

**Deliberately not phased at all** — see §5 for why: real-time
collaboration, enterprise governance tooling, a desktop sync client,
semantic AI search, a native mobile app.
